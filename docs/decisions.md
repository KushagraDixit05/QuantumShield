# Decisions
- D-001 Scope: `plan/` contains the MVP plan (Phases 0-5), not the 8-phase plan in the brief. Build MVP first; SGD spot-check, Merkle data, Falcon/SLH-DSA are post-MVP. (user-approved)
- D-002 No mock crypto: the plan's day-1 mock ZK backend is dropped; real RISC Zero only, else the fallback ladder. (user-approved)
- D-003 Python 3.11.17 obtained via uv into .venv (system 3.12.3 not used). liboqs-python builds liboqs 0.16.0 from source (no dilithium-py fallback needed).
- D-004 CI/Docker are "deferred" in the plan but requested in the brief: minimal CI + Makefile included.
- D-005 Roadmap files: the brief names `plan/00_README_Overview.md` and `Phase_N` files; they do not exist. `plan/` holds only the MVP files (`00_MVP_Overview.md`, `MVP_Phase_0..5`, `99_MVP_Risks_and_Cuts.md`). Those are followed; the approved MVP plan wins where it conflicts with the brief, except D-006..D-008.
- D-006 ZK statement scope: the brief asks the Phase 0 statement to include K SGD steps on Merkle-committed data; the approved plan deferred that. The written statement (`docs/zk_statement.md`, in place of the planned `mvp_statement.md`) includes it as the target relation. Phase 3 may fall back to commitment + norm only via the cut ladder; the statement says so.
- D-007 Attack suite: scaled, sign-flip, label-flip, replay (brief) instead of the plan's single scaled/noisy attack.
- D-008 Fixed point from Phase 1 (brief) instead of a float PyTorch baseline: the baseline is a pure-integer numpy MLP (int64, scale 2^16, arithmetic-shift flooring). PyTorch is not used for FL training.
- D-009 Loss: one-hot MSE on linear outputs (gradient = out - onehot). Exactly integer, no exp/log, easy to port to the guest. Fallback if accuracy is too low: integer LUT softmax.
- D-010 Dataset: sklearn digits (64->32->10, 2,410 params), IID split over 5 clients, no download. Pixels 0..16 map exactly to fixed point via `<< 12`.
- D-011 FL hyperparameters (K=20 steps, batch 32, lr 0.3, init N(0, 0.1^2) for both layers) were tuned on seeds 100-104 (disjoint from evaluation seeds 0-4). The first choice (He-scale init) gave very large, seed-dependent round-0 updates (benign ||Δ|| up to 4.6) and 0.88 ± 0.03 accuracy, which would have forced a loose B. B is calibrated on seed 100 (benign updates, 99th percentile x 1.5). K=20 keeps the future in-guest SGD recompute small.
- D-012 Diverged runs: with int64 fixed point, a scale-50 update under plain FedAvg drives the model out of range. Such a run is recorded as accuracy 0.0 from the divergence round and flagged "diverged". This is a convention, not a measured accuracy; tables show the divergence count.
- D-013 `norm_filter` in Phase 1 is a plaintext comparison of ||Δ||^2 against B^2. It is the policy the ZK proof will enforce later, but it is NOT a proof and does not hide Δ. An update whose norm overflows the exact int64 computation is rejected (it would be unprovable).
- D-014 Phase 2 envelope and scope. The brief's envelope (domain tag, round, client id, H(W_t), C_i, Merkle root R_i, nonce) replaces the plan's `(version, round, client_id, C, proof_hash, nonce)` and the §7 list in `zk_statement.md`; there is no proof yet, so no `proof_hash`. Falcon-512, SLH-DSA-128s, hybrid and per-epoch key rotation, listed as "Deferred" in `plan/MVP_Phase_2_PQ_Signatures.md`, are built because the brief asks for them. Benchmark compares against Ed25519 (brief) rather than ECDSA-P256 (plan). `R_i` is a real `fl/merkle.py` root over each client's samples (the first use of that code); the aggregator does not check R_i against anything yet, it is only bound by the signature (the ZK proof will check it, Phase 3). Phase 1 settings (data, model, K, batch, lr, B, 10 rounds, 5 clients) are unchanged.
- D-015 Algorithms and randomness. `SLH-DSA-128s` = liboqs `SLH_DSA_PURE_SHA2_128S` (FIPS 205, pure, SHA2). liboqs-python has no seeded keygen and this liboqs build does not export the NIST-KAT seeding call, so `pq/sig.py` installs liboqs's `OQS_randombytes_custom_algorithm` hook fed by a SHA-256 counter stream: with a seed, keys and signatures are bit-reproducible for a fixed call order in one thread. This is a test/experiment RNG, not for production use. Ed25519 keys are derived from the same stream. Benchmark timings use the system RNG (callback overhead would distort them).
- D-016 What a signature covers. Signed bytes = domain tag || alg label || payload (update tag `QSFL-env-v1`, vote tag `QSFL-vote-v1`). The delta itself travels in the clear (D-013 / zk_statement §5) and is bound to the signature through C_i = SHA256("QSFL-upd" || Δ || nonce); the aggregator recomputes C_i from the received delta, so altering Δ after signing is rejected. Signatures authenticate the sender and bind round and model hash. They do NOT detect a client that honestly signs a poisoned update, nor a stale delta re-signed under a fresh round and nonce (the Phase 1 `replay` attack): only a verbatim resend of an old envelope is caught. The latter needs the ZK proof's binding to H(W_t) (Phase 3). Hybrid requires exactly {Ed25519, PQ}; any other signature set is rejected as `scheme_downgrade`/`unsigned`. `signatures: none` takes the unchanged Phase 1 path (explicit config, so the "no unsigned path" exit criterion holds for every mode except none). Nonces are tracked per (client, nonce) across rounds and one submission per (client, round) is allowed; nothing is remembered until all checks pass.
- D-017 Phase 3 training size inside the proof. Measured cost (docs/zk_cost.md): K=1, batch 32 took 981 s and 6.4 MB; K=20, batch 32 extrapolates to about 4.5 h. Chosen: K=2, batch 4, segment po2 18, composite receipt (377 s, 2.42 GB peak, 3.0 MB). Phase 1/2 settings (K=20, batch 32) are not changed; `configs/phase3.yaml` carries the smaller values, with B recalibrated for them and the non-ZK reference rerun at the same K/batch. In FL runs only a configured subset of (round, client) pairs is proved with real receipts, because proving all 50 would take about 5 hours; the report states which pairs were proved. po2 20 ran out of memory. Statement scope is unchanged: relation 1 (full) is proved, only with this K and batch. User approved the reduce-K/batch fallback and envelope v2 with proof_hash before the measurement.
- D-018 Envelope v2 (user-approved). Update payload version byte 2 appends `proof_hash` = SHA256(receipt file bytes) (170 B); v1 (138 B) still parses and is used when `zk` is off. `Verifier(..., zk=ZkPolicy)` makes a v2 envelope plus receipt mandatory: `verify_envelope(env, delta, receipt=None)` keeps the `(ok, reason)` return, with reasons `bad_proof:{missing_proof_hash, missing_receipt, hash_mismatch, unknown_client, <verifier reason>}`. The proof check runs after the commitment check and before nonce bookkeeping, so a bad proof does not burn a nonce. `pq/zkpolicy.py` builds the expected 146-byte journal from the signed envelope fields plus trusted run configuration (n_c, K, batch, seed, lr_fx, B2). The nonce is carried in clear in the envelope although `zk_statement.md` lists it as private witness; Δ is public in the MVP so nothing extra leaks. The Phase 1 test `test_no_zkvm_dev_mode_in_repo` was narrowed to forbid enabling dev mode outside `tests/zk` (the host must be allowed to mention the variable in order to refuse it).
- D-019 Supersedes D-017. Agent A's optimised guest needs about 2.7x fewer cycles than the probe, so the same proof budget buys K=4, batch 8 (3.01M total cycles; real proof 381.9 s, 2.42 GB peak, 3.06 MB receipt, verify 0.17 s; docs/zk_cost.md). `configs/phase3.yaml` uses K=4, batch 8, B=0.9482 (seed 100, p99 0.6321 x 1.5, Phase 1 rule); benign accuracy at this size reaches about 0.76 after 10 rounds on the calibration seed (Phase 1: 0.94 at K=20, batch 32). The cut from K=20, batch 32 stays: that setting is about 4.5 h/proof with the probe guest and untested with the production guest. Interface v1.3 settled three ambiguities found by Agent C (opening x = 512 bytes, relation 2 has no n_open, K and batch must be 0 for relation 2). The guest also enforces lr_fx > 0 for relation 2 (Agent A's reading of "always"; accepted).
- D-020 Phase 4/5 scope (user-approved). The brief's Phase 4 (verifiable consensus with view change, partial synchrony, leader rotation, network simulator, certificate ledger, n up to 16) and Phase 5 (evaluation E1-E7, non-IID, ablations, 100k-parameter ZK scaling) do not match the approved MVP plan, where Phase 4 is consensus-lite (4 nodes, f=1, fixed leader, no view change) and Phase 5 is the demo/proof-of-work package. The MVP plan is followed. The brief-only items are deferred (docs/deferred.md). The "committed to repo" screen recording from the MVP Phase 5 task list cannot be produced by the assistant; a script is provided instead.
