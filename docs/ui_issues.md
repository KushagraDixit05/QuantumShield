
## B1 (backend) findings
- UI-B1-1 `demo/run_demo.py:run_scenario` hardcodes `Node(defence="fedavg")`, so the aggregator choice cannot be passed through it. `backend/runner.py` mirrors its loop instead; `tests/backend/test_runner.py` fails if their fedavg accuracies, accepted sets, rejects or divergence rounds drift apart.
- UI-B1-2 `run_scenario` treats "no finalization" as divergence for both causes (int64 overflow, D-012, and a round that gets fewer than 2f+1 matching votes) and scores both 0.0. The backend separates them (overflow -> `diverged`; no quorum -> `not_in_quorum` rejection with `client: null`). In the shipped configuration no-quorum cannot occur (all four nodes are honest); it is only exercised in a test with silent nodes.
- UI-B1-3 `consensus.node.Node` keeps only vote hashes (`_Round.voted`), not the signed vote envelopes, so a certificate (the round's signed votes) cannot be read from Node state alone. Worked around without touching consensus code: `backend.runner.RecordingNetwork` (a `Network` subclass) records each `Vote` that nodes broadcast. If Node is ever changed to retain envelopes, this subclass can go.
- UI-B1-4 Certificates verify with `KeyRegistry.from_snapshot` (public keys only) and `Verifier.verify_vote`, but `Registry.status()` calls a key `stale` unless its epoch equals `registry.epoch`. A snapshot taken at the end of a run has the last epoch, so rounds from earlier epochs would fail as `stale_key`. The backend sets `snapshot["epoch"] = round // epoch_rounds` on a copy of the public snapshot before verifying (no code change; public data only). A round-5 certificate is tested.
- UI-B1-5 `docs/api_contract.md`: `GET /api/zk/rounds` says `status` is `verified|no_receipt|rejected`. The backend also returns `unverified` when a receipt exists but verification could not be run (binary missing, no expected public journal), because reporting `verified` or `rejected` there would be a guess. The contract should list it. Extra, undocumented endpoint added: `GET /api/certificates/{run_id}/{round}` (the pasteable certificate); `GET /api/consensus/{run_id}` takes an optional `?seed=`.
- UI-B1-6 `*.stats.json` files do not exist under `demo/results/zk/`; prove_s, cycles and peak RSS per receipt come from `demo/results/phase3_fl.csv` (same run), and `source` on the response is not extended per field. The 4 receipts in `demo/results/zk/bench/` are not listed (they are a different set; see zk_bench.csv).

## Lead findings
- UI-001 `docs/evaluation.md` (named in the UI brief) does not exist. The limitations list is `docs/limitations.md` (5 headings, 19 items); the Limitations panel reads that file and cites it. Results live in `demo/results/`, not `experiments/results/`.
- UI-002 The consensus layer has no certificate type, no certificate-verify function, no view changes and no leader rotation (fixed leader 0; deferred by D-020). The UI treats a "certificate" as the round's 2f+1 signed votes captured from the simulated network (see UI-B1-3) and verifies each vote with public keys only. This verifies votes, not a chained certificate; the UI states this. A real certificate chain needs consensus work that is out of scope here.
- UI-003 `*.receipt` files carry no id, date or hardware metadata. Receipt id = first 12 hex chars of sha256 of the file; "generated" = file modification time; hardware is parsed from `demo/results/zk_bench.md` and `docs/zk_cost.md`. The UI labels these sources.

## C findings (custom mode and multi-seed e2e, tests/e2e/custom_multiseed/)
- UI-G-1 (known gap, not fixed) The /run page has no mean ± std line over the chosen seeds. It shows per-seed final accuracy, per-round accuracy per seed and the rejection log only. The multi-seed checks recompute mean and std from the displayed per-seed finals and compare them with scenarios.csv, the Overview summary table and the attack heatmap.
- UI-G-C-1 Std is defined two ways. Overview `SummaryTable` shows `std (n-1)` (sample std, 0.0162 for none/off over seeds 0-4); the attack heatmap prints "± 1.4%" for the same cell because `backend/results.py:31` uses `statistics.pstdev` (population std, n). The heatmap does not say which. Test `5-seed preset A ... attack heatmap cell` fails on this (UI 1.4 vs 1.62 percentage points). Fix either by using `statistics.stdev` in the backend or by labelling the heatmap "std (n)".
- UI-G-C-2 `tests/e2e/shared/runner.ts chooseCustom` cannot select Attack or Defence: `getByLabel(/^Attack$/)` and `/^Defence$/` match nothing because the wrapping `<label>` text includes the option texts ("Attack scaledforgedreplay"), so any spec using it hangs until the test timeout. Fix in RunView.tsx by giving the selects `aria-label` / `id`+`htmlFor`, or fix the helper selectors. custom_multiseed uses a local replacement in `util.ts` meanwhile.
